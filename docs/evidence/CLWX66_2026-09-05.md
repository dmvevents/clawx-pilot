## What "the production surface" is for classification

The taxonomy is persona/product-doc-encoded, not a standalone registered tool.
`docs/PRODUCT_PRINCIPAL_ASSISTANT.md` line 171 documents the closed set the
assistant routes to and states the class is "returned alongside extracted
fields":

```
MoE_circular, parent_letter, staff_leave_application, attendance_report,
inventory_form, meeting_minutes, disciplinary_record, other
```

There is no `document.classify` tool in `extensions/moe-principal-assistant/index.mjs`
(grep of the whole plugin: the taxonomy strings appear only in the product doc
and board, not in code). Classification is therefore an LLM behaviour driven by
the plugin's real persona system prompt. So the e2e drives the **actual persona
`SYSTEM_PROMPT`** (imported live from `extensions/moe-principal-assistant/persona.mjs`
— the exact prompt the host prepends when the plugin is enabled) plus a
classification instruction that fixes the product-doc taxonomy as the closed set
of allowed answers, over text that came through the **production document
reader** (`doc-tools.mjs` `writeDocx` -> `readDocx`/mammoth, the same round-trip
`scripts/clwx63-extract-chain-e2e.ts` uses). The model call uses the same
Bedrock InvokeModel lane as clwx63.

This is plugin-direct (import + execute the extension surface + one direct model
call). It does **not** drive the running app / gateway chat session — that lane
was in use by another agent (wp-clwx67-reminder) and is off-limits per the task.
