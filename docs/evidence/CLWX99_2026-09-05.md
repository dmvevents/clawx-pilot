# CLWX-99 — Cron timezone fix: schedules resolve in the principal's wall-clock

**Date:** 2026-09-05 · **Verdict: FIXED in-tree** (10/10 new units green with demonstrated
falsifiability; live check proves the defect on the running pre-fix build AND the mechanism
the fix rides)

## Root cause, confirmed live

- **Cron exprs:** the gateway resolves `schedule.tz` when present, else the timezone its own
  process cached at first use (`resolveCronTimezone` in the bundled gateway `schedule-*.js`).
  The running gateway (up since Sep 3, no `TZ` env) still resolves `Asia/Calcutta` while
  `/etc/localtime` is `Asia/Dubai` — a boot-time ICU cache from before a system zone change.
  This is exactly the "laptop tz change without app restart" fleet path.
- **`kind:"at"` timestamps:** the gateway's `normalizeUtcIso` APPENDS `Z` to zone-less ISO
  strings — naive = UTC unconditionally; `tz` is never consulted on this branch. An ISO with
  an explicit offset passes through untouched and parses correctly.

## The fix (all app-side creation surfaces + the agent surface)

| Surface | Change |
|---|---|
| `electron/utils/cron-tz.ts` (new) | `systemTimeZone()` reads the OS truth fresh per call (`/etc/localtime` symlink on macOS/Linux, validated against Intl; Intl fallback on Windows) — deliberately NOT the process-cached Intl zone, which goes stale exactly like the gateway's. `cronScheduleFrom(expr)` / `reminderSchedule()` are the shapes every surface must produce. |
| `electron/api/routes/cron.ts` POST | `schedule: cronScheduleFrom(input.schedule)` — every job created through the app carries `tz`. |
| `electron/api/routes/cron.ts` PUT (`buildCronUpdatePatch`, now exported for the unit) | bare expr strings get the full tz'd shape; a cron schedule OBJECT without `tz` gets the system zone added; an explicit `tz` is never overridden. |
| `electron/main/moe-seed.ts` | seeded 3:30pm fleet reminder uses `reminderSchedule()`; **repair path added** — found-by-name idempotency would otherwise never deliver `tz` to already-seeded installs, so an existing reminder missing `schedule.tz` is patched via `cron.update` (returns `repairedTz: true`). |
| `extensions/moe-principal-assistant/persona.mjs` | agent-side rule for the `cron` tool: one-off `at` timestamps MUST carry an explicit UTC offset (computed from the current-time header, which shows local + UTC); recurring exprs must set `schedule.tz`; states the failure mode ("stored as UTC and fires hours late"). This is the fork-side lever for the defer-write defect — the `cron` tool itself lives in the bundled gateway package, and patching upstream dist mid-pilot is out of scope. |

## Residual risk (stated honestly)

- The agent-side fix is prompt-level (the `cron` tool is upstream gateway code). The persona
  rule + the current-time header give the model everything needed to emit offsets; the unit
  guards the rule's presence, not the model's compliance. A live defer re-run belongs in the
  next clwx67 harness pass (assert the follow-up job's `at` carries an offset).
- Windows `systemTimeZone()` falls back to process-cached Intl (no /etc/localtime): fresher
  than gateway-boot but stale across an OS zone change while the app runs. Trinidad's fixed
  UTC-4/no-DST makes this a dev-machine class, not a fleet class.
