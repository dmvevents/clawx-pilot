# Problem → Root-Cause → Fix Map (2026-09-04)

Consolidated RCA across 9 defect clusters mined from the blocker collection, the Karunesh error ledger (K-series), the defect register, and the Plane board (CLWX-series). Every root-cause row was verified against source at `file:line` and then passed through an adversarial verifier pass. Where the verifier **refuted** a root cause or corrected an attribution, this map carries the **corrected** version, not the original card text.

Analysis only. This document recommends fixes; it changes no source. All conclusions rest on static source reads (per the RCA discipline: `build/`/`dist/` never read).

**Headline: the fleet is overwhelmingly our own code, not the vendor or the environment.** 36 of 51 rows are ours outright; even the 11 "mixed" rows have an external *trigger* (a Chrome M136 security change, a rotated Outlook DOM, a Windows share violation) but the *defect* is our failure to adapt to a constraint we had usually already documented. Only true off-repo process failures (the WhatsApp credential paste) sit outside the code.

### The 5 sharpest findings

1. **Chrome CDP still cannot attach on a fresh box (RCA-CHROME-CDP-DEFAULTDIR / K1 / K2 / CLWX-73) — email GA-blocker, LIVE.** The self-launch uses the *default* Chrome user-data-dir, which Chrome M136+ silently refuses remote-debugging on, so `:18792` never binds. The dangerous managed-Chromium fallback was correctly deleted (trust risk closed), but functional attach was never restored — the replacement path *still* launches the default dir. Our own probe (`pilot-probe-state.ps1:54-58`) and the demo launcher (`pilot-attach-chrome-cdp-demo.ps1`) already documented and worked around this; the shipped launcher did not adopt the workaround. Compounded by a no-kill loop that misreads our own failed launch as a user profile-lock and ping-pongs `diagnose→close→repair→timeout`.

2. **NEW: packaged doc-parsers resolve only by luck of the install path (K8) — documents GA-blocker, LATENT.** `CLAWX_APP_RESOURCES` is never set by the app; `augmentModulePathsForPackagedApp` is Windows-only and hardcoded to the default per-user install path. The extension sits at `resources/extensions/`, a *sibling* (not ancestor) of `resources/openclaw/node_modules`, so `createRequire` walk-up never reaches the parsers. It works today only because dev runs beside the repo `node_modules` and the default Windows install path matches the hardcode. **macOS-packaged and relocated-Windows installs are unproven latent parser failures.** One-line fix: set `CLAWX_APP_RESOURCES=process.resourcesPath` in `forkEnv` when packaged.

3. **Statutory forms can still fabricate attestations (CLWX-79) — data-integrity, LIVE (residual).** The primary silent-backfill path is fixed (missing required fields now refuse). But demo-default fabrication remains reachable two ways: `demo` is an **LLM-settable tool parameter** on `forms.preview_suspension` (index.mjs:1701) *and* on the daily-report builder (index.mjs:973), and `process.env.DEMO==='1'` is **overloaded** with the fill-scripts' "actually submit for real". Invented values (e.g. `written_reports_collected:'Yes'`) do reach the DOM and are submittable. Verifier corrected attribution **mixed→ours** (every component is fork-authored) and flagged the fix as incomplete (must stop *reading* `args.demo`, not just drop the schema field; must close *both* demo params).

4. **Mid-turn channel degrade orphans/replays turns (CLWX-95 / CLWX-94 / CLWX-96) — resilience GA-blocker, LIVE.** The cloud→on-device degrade applies via a debounced gateway *restart*, and the resend races the restart, so the turn dies with no terminal event and the renderer spins. `lastSentPayload` is cleared only on `final`, so an orphaned prompt stays set and the history-poll failover **replays it as a fresh user turn** (one observed run chained a WRITE tool call with no human present). After hosts-restore the "offline" banner never clears without a full relaunch. Verifier warning: the naive "null `lastSentPayload` in the error handler" fix would *defeat* the auto-resend feature — it must be cleared only after the degrade attempt consumes it.

5. **The exposed gateway key is baked into the shipped installer, not just pasted to WhatsApp (CLWX-19 — REFUTED).** The verifier refuted the card's "code side is clean": the `sk-clawx` key is a *gitignored* resource (`resources/cloud-gateway.json`, `.gitignore:71-72`) baked into the build and persisted **plaintext** to `clawx-providers.json` on first boot. The empty git pickaxe proves only "not in committed history." Rotation alone re-bakes a new exposable key; with auto-update OFF, server-side rotation also causes a fleet-wide cloud outage requiring per-machine re-key.

## 2. Methodology note (RCA discipline)

- **Evidence-first.** Every root-cause claim is anchored to `file:line` in source we can read (`electron/`, `src/`, `extensions/`, `scripts/`, `tests/`, `docs/`, `windows-pilot/`). `build/`/`dist/` were never read (baked-secret constraint), which is itself an open-question source for gateway-internal behaviour.
- **Competing hypotheses.** Where a symptom had more than one plausible mechanism (e.g. CLWX-96 silent send: restart-race vs four-store mismatch; CLWX-91 blank e2e: render throw vs unresolved async vs missing mock), the map names the rival hypothesis rather than asserting one.
- **Adversarial verify.** Each card's root cause, fix, and attribution were independently re-checked. The verifier confirmed most, refuted 2 root causes (CLWX-19, CLWX-91), corrected 2 attributions (CLWX-79, K9), and downgraded 8 "simple" fixes.
- **Could-it-be-our-error is a first-class lens.** Default suspicion is our code. External triggers (Chrome M136, Outlook DOM rotation, Windows AV share violation, Plane HTML-only fields) are labelled **mixed**, never used to excuse the defect. Cards that trusted a stale "already fixed" note were re-verified against current source (several were stale, e.g. K1's managed-fallback note, CLWX-36's named commit).
