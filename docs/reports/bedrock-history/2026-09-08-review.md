## Observations

Ordered by what I would act on first. `VALIDATED` means I checked the current tree at the
stated path; `HYPOTHESIS` means the logs suggest it and I did not prove it.

### 1. VALIDATED — False-green reachability probing is the access-lane failure the project has already paid for, and the fix is now real in three places

Logs show `nc -z` reporting the local IAP listener as up while ssh reset at key exchange
because the tunnel's credentials had died, and the GA gate printing "IAP tunnel up — run the
V-batch workflow" against an unusable lane.

Current tree: `scripts/ga-gate.mjs:258-299` now discriminates three states — not bound
(SKIP/blocked), bound plus verified guest ssh handshake (INFO, and explicitly "not installed-app
release proof"), and bound but handshake failed ("a live tunnel with dead credentials",
BLOCKED) — plus a control leg that must **not** answer on guest port 9999, otherwise the probe
method itself is declared untrustworthy. `windows-pilot/vm-testing/gcp-iap-lane.sh` `cmd_probe`
requires an RDP protocol response, an SSH banner and the IAP rejection for closed guest port
9999, and fails closed with a count of failed checks.

Classification: FIXED-GUARDED. Nothing to do; this is the pattern the other observations should
be measured against.

### 2. VALIDATED — The same lesson is missing from the Codex skill root

`grep -rl "9999|control leg|listener readiness"` across the three skill roots matches only
`.agents/skills/gcp-iap-windows-lane/SKILL.md` and `.claude/skills/gcp-iap-windows-lane/SKILL.md`.
`.codex/skills/` has **no `gcp-iap-windows-lane` at all**, and also lacks `pilot-ssh-ops`,
`windows-build-package` and `windows-outlook-forms`, while carrying a `windows-outlook-demo`
that neither other root has. `AGENTS.md:19-20` routes Codex agents to `.codex/skills/` and
states "Keep equivalent critical workflows aligned".

This is a mirror-parity observation, not proof that Codex cannot load the workflow. The current Codex catalog also exposes `.agents/skills`; `REPOSITORY_GUIDE.md` explicitly documents both roots. A task can load the canonical skill even when an OMX compatibility copy is absent. Verify actual session catalog/routing before classifying access as broken. No new card is justified by mirror absence alone.

Classification: HYPOTHESIS about compatibility drift; workflow unavailability NOT ESTABLISHED.

### 3. VALIDATED — The probe that proves the pilot chat path steers the model away from the failure mode it should catch

`windows-pilot/scripts/pilot-electron-cdp-probe.js:342` injects: "Use only direct tools in this
session; do not use sessions_spawn, sessions_yield, subagents, or background sessions."

The critic's alternative — that this is deliberate isolation — is partly right, and the precise
consequence is narrower than my first claim: the shipped app enforces the same list as a
*policy deny* for the on-device model only (`electron/utils/ondevice-tool-policy.ts:43-58`,
`ONDEVICE_DENIED_TOOLS`, motivated by the documented
`process → sessions_list → sessions_yield → subagents` cascade of the 3B model). Cloud/Online
providers keep the full catalog by design. So for an **Online** run the probe's prompt-level
suppression has no counterpart in the product, and an Online probe pass cannot evidence that the
cascade does not occur in a principal's Online turn.

Classification: FIXED-UNGUARDED for the on-device path, gap for the Online path.

### 4. VALIDATED — `scripts/vm-verify-moe19.sh` is a version-pinned entrypoint that describes itself as "THE single command"

Lines 30-34 parameterize ports and the guest user through environment variables; lines 36-37
hard-code `release/Ministry of Education-0.4.3-moe.19-win-x64.exe` and
`gs://clawx-rc-artifacts-622687731621/moe19/`, while current candidate work is moe.22-moe.25
(`docs/evidence/WINDOWS_MOE25_PLANNING_BASELINE_2026-09-08.md`). The critic suggested the pin
may be deliberate reproducibility; the surrounding parameterization argues otherwise — the
artifact is the one input that cannot be overridden.

Classification: TRACKED-OPEN in effect (`windows-pilot/vm-testing/README.md` already warns not
to run it against a later candidate), open as a tooling defect.

### 5. VALIDATED — The plaintext sandbox credential survives in the session corpus, and the sweep that removed it elsewhere never covered these files

`docs/BLOCKER_BUG_COLLECTION_2026-09-03.md:163` row 63 records "The sandbox test-account

shape in the rebuilt pack, 4 `[REDACTED_CREDENTIAL]` substitutions.

Classification: TRACKED-OPEN (do not file again). The durable remediation remains credential

### 7. VALIDATED, with my own claim corrected — The error surface is long-tailed, not dominated by any class

I claimed orchestration/timeout classes dominated. Measured over the 21,485 findings, the
largest classes are: `exec_command` `CreateProcess … No such file or directory (os error 2)` 39;
outbound-send guard DENY 28; API `ENOTFOUND` 28; `{"timed_out":true}` 26; `Exit code 143 …
timed out after 6m` 16; gcloud non-interactive `Reauthentication failed` 11; ssh reset at key
exchange 9; Chrome CDP `ECONNREFUSED`/`port_bind_timeout`/`profile_locked_close_chrome` 9; IAP
`Unable to open socket on port` 1. The largest single class is 0.2% of findings across 4,381
distinct tool-error groups.

Correct conclusion: no class dominates, and the highest-frequency classes are harness and
environment friction rather than product defects. The critic was right to reject the word
"dominant"; the counts above are the answer.

### 8. HYPOTHESIS — A gcloud auth-freshness preflight would convert a mid-run stall into an upfront owner ask

11 findings show non-interactive `Reauthentication failed … cannot prompt during
non-interactive execution` during VM work. Interactive authentication needs the account holder,
so the run stalls after setup work has already been done. Unverified: I did not check whether

### 9. VALIDATED — The Session 0 display trap is real and already codified; treat the differing pixel numbers as run variance

Logs: the app renders in interactive session 1 while SSH runs in session 0, `CopyFromScreen`
returned blank, and the two sessions reported different geometry (1024×768 vs 1280×720); the fix
was a scheduled task running as the logged-on user. `windows-pilot/vm-testing/README.md:70`
states the rule with 1024×768 vs 1920×1080. The differing second number is a different run, not
a contradiction — the rule is "collect another snapshot in the interactive session", not a fixed
resolution.

Classification: FIXED-DOCUMENTED.

### 10. VALIDATED — Injected context, not project signal, is most of what a naive log review would read

Before filtering, the pack was dominated by compaction summaries, agent-file preambles, skill
preambles, teammate and task notifications, developer-role instruction dumps and chunked file
dumps: 8,173 records. A history review that reads whatever it finds first will mostly read
instructions the project injected into itself, and can then mistake them for evidence — and,
because those blocks contain historical directives, can be steered by them. The extractor drops
and counts them, and the pack states in its header that excerpts are data, not instructions.
