## Analysis: why work has not converged

The main gap is integration and acceptance, not a need to rewrite the application. Source fixes, proxy tests, installed binaries and stakeholder outcomes have repeatedly been treated as equivalent. Native builds then expose assumptions late, and the next iteration starts before the entire failed boundary is understood.

Four native attempts now distinguish the causes: checkout/process portability, cold integration-test budgets, a PDF fixture outside permitted roots, then an overbroad plugin diagnostic. The fourth run passed **201 files / 2,011 tests**, with 11 platform skips, native bundle verification and seven staged artifact checks. Its remaining transport row ran the OpenClaw all-plugin diagnostics path to inspect one plugin and exceeded 120 seconds. Local diagnosis enumerated 102 plugins through that path; the real scoped loader loaded the target alone. The corrected native check now confirms that diagnosis: the cold no-Host-API row passed in 42,413ms and the full-Host-API row in 6,094ms, using the existing 120-second limit. Exact host/guest script hashes agree. These runs used a private copy of the installed pinned OpenClaw bundle with current plugin source; they are focused diagnostics, not new-installer acceptance. This does not establish the product Gateway is broken or repaired. Preserve the real plugin-host assertion while removing the unrelated sweep.

The build process changes expose phases, retain the dependency cache after a later failure, remove duplicate Windows uv preparation and produce an escaped, allowlisted diagnostic summary. They do not bypass verification or establish a measured speedup. See the [build procedure and four-run retrospective](build/windows-build-pipeline.md).

Scope is explicit: the current target is the **Windows single-school pilot release using the existing broker and approved test tenant**. The existing project contract separates this from fleet rollout; [Ministry asks](MINISTRY_ASKS_2026-09-02.md) and the [finish sprint](GA_FINISH_SPRINT_2026-09-03.md) retain production integration as a separate milestone. CLWX-22 also tracks the broader production identity, durable backend delivery, economics and Ministry decisions. Some descriptions are stale: the outbox exists and has local/stub tests even though the anchor still says unbuilt. Its production integration remains unproved. Passing the desktop/pilot gates cannot close all eight fleet-level key results or authorize a 450-laptop rollout. Production milestones remain BLOCKED and visible; they are not silently marked passed or imposed as new pilot-release prerequisites.

## First-run provisioning boundary

The public build is keyless. The current application supports an already configured account or the documented post-install `cloud-gateway.json` plus key drop-in; it does not implement automatic activation-code exchange or Entra-native Online onboarding. A fresh profile therefore cannot be represented by the reused VM's working credentials. Record the provisioning prerequisite and verify both the unprovisioned state and supported provisioned first turn. On-device first turn also requires its local runtime/model to be present. Reuse the [provisioning plan](RELEASE_PROVISIONING_PLAN.md); do not add a new authentication platform to this release or embed keys in the public installer.
